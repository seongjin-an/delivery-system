# 기술 선택 근거

같은 일을 다른 방법으로도 해보고, 그 결과를 여기 표로 남긴다.
읽어서 아는 것과 겪어서 아는 것의 차이를 기록으로 남기는 게 목적이다.

측정은 전부 같은 노트북(8코어, 16GB)과 같은 도커 컴포즈로 했다. 부하는 절마다 다르니
각 절 첫머리에 적는다.

---

## 1. 아웃박스를 카프카로 내보내는 방법 — 폴러 vs Debezium CDC

부하: 주문 100건을 order-api 두 대에 번갈아 넣었다.

주문 행과 이벤트 행을 한 트랜잭션에 넣는 것(아웃박스 패턴)까지는 같다.
다른 건 **그 이벤트 행을 누가 카프카로 옮기느냐**다.

| | 폴러 (OR-06) | Debezium CDC |
|---|---|---|
| 옮기는 주체 | 앱 안의 스케줄러 | 카프카 커넥트 (별도 프로세스) |
| 읽는 곳 | `outbox` 테이블 | MySQL binlog |
| 인스턴스 여러 대 | `FOR UPDATE SKIP LOCKED` 로 나눠 집는다 | 커넥터가 한 곳이라 신경 쓸 게 없다 |
| DB 부하 | 200ms 마다 SELECT + UPDATE | 없다 (binlog 를 따로 읽는다) |
| 필요한 인프라 | 없다 | 커넥트 컨테이너 + 복제 권한 |

### 지연 (아웃박스 INSERT → 카프카 발행)

| | 최소 | 중앙값 | 평균 | p95 | 최대 |
|---|---|---|---|---|---|
| 폴러 | 58ms | — | **297ms** | — | 901ms |
| CDC | 5ms | 16ms | **33ms** | 140ms | 143ms |

평균이 9배 차이 난다. 폴러가 느린 건 코드가 나빠서가 아니라 **구조가 그렇게 생겨서**다.
주기가 200ms 면 방금 들어온 행은 평균 100ms 를 그냥 기다린다. 거기에 한 배치(100건)에
다 안 들어간 것들이 다음 주기로 밀리면서 꼬리가 길어진다. 최대 901ms 가 그 꼬리다.

CDC 는 기다리는 구간 자체가 없다. binlog 에 적히는 순간 읽어간다. 중앙값 16ms 는
사실상 "MySQL 이 커밋하고 커넥트가 카프카에 쓰는 시간" 이다.

### 그럼 폴러는 왜 먼저 만들었나

`SKIP LOCKED` 를 직접 겪어보려고 그랬다. 세션 두 개로 재본 결과가 이렇다.

| 쿼리 | 응답까지 | 받아간 행 |
|---|---|---|
| `FOR UPDATE SKIP LOCKED` | 275ms | 114, 115, 116 (다른 행) |
| `FOR UPDATE` 만 | 3787ms | 111, 112, 113 (**같은 행**) |

`SKIP LOCKED` 를 빼면 두 겹으로 깨진다. 뒤에 온 인스턴스가 앞사람을 기다리느라 늘린 의미가
없어지고, 기다린 끝에 받는 게 앞사람이 방금 발행한 그 행이라 카프카에 중복이 나간다.

CDC 로 가면 이 문제 자체가 사라진다. 사라지는 게 아니라 **커넥트 쪽으로 옮겨간다** —
커넥터를 두 개 띄우면 같은 binlog 를 두 번 읽어서 똑같이 중복이 난다. 다만 커넥트는
"커넥터 하나에 태스크 하나" 가 기본이라 우리가 실수하기 어려울 뿐이다.

### 대가

공짜는 아니다.

- **컨테이너가 하나 늘었다.** 메모리를 1GB 쯤 더 쓴다.
- **장애가 앱 밖으로 나갔다.** 이벤트가 안 나갈 때 앱 로그를 봐도 아무것도 없다.
  `curl localhost:8083/connectors/order-outbox-connector/status` 를 봐야 한다.
- **커넥터가 안 떠 있으면 이벤트가 한 건도 안 나간다.** 폴러 때는 앱만 살아 있으면 됐다.
  `scripts/start.sh` 가 등록까지 해주지만, 인프라를 부분만 띄우면 조용히 멈춘다.
- **처음 붙일 때 기존 행은 안 읽는다** (`snapshot.mode=schema_only`). 우리는 폴러가 이미
  내보낸 것들이라 이게 맞는 선택이지만, 처음부터 CDC 로 시작한다면 `initial` 이어야 한다.

### 겪은 것

**커넥터가 RUNNING 인데 이벤트가 한 건도 안 나갔다.** 상태만 보면 멀쩡했다.
커넥트 로그를 보니 `delivery` 라는 토픽에 계속 쓰려다 실패하고 있었다.

```
Error while fetching metadata ... {delivery=UNKNOWN_TOPIC_OR_PARTITION}
```

Debezium MySQL 커넥터는 DDL 변경 이벤트를 `topic.prefix` 와 같은 이름의 토픽에 쓴다.
우리는 파티션 수를 못 박으려고 브로커의 auto-create 를 꺼놨으니 그 토픽이 없고,
커넥터는 거기서 막힌 채 아웃박스 이벤트를 하나도 못 내보냈다.
`include.schema.changes=false` 로 껐다.

교훈은 "커넥터 상태가 RUNNING 이라고 일이 되고 있는 게 아니다" 다.
태스크는 살아 있어도 프로듀서가 못 쓰고 있을 수 있다.

### 그래서 어느 쪽을 쓰나

**CDC 를 기본으로 둔다** (`delivery.outbox.mode=CDC`).
폴러 코드는 지우지 않고 `mode=POLLER` 뒤에 남겨뒀다. 같은 조건에서 다시 재보려면 필요하고,
커넥트 없이 앱만 띄우고 싶을 때도 쓸 수 있다.

## 2. 위치 스트림 — 카프카 vs 래빗엠큐

부하: k6 로 location-ingest 에 초당 3000건(라이더 3000명이 1초마다). 컨슈머는 둘 다 3개씩,
한 번에 최대 500건씩 받는다. 래빗엠큐 4.3.6 클래식 큐, cp-kafka 7.6.1 단일 브로커.
실험 코드와 측정 원본은 `exp/location-rabbitmq` 브랜치의 `experiments/location-transport/` 에 있다.
main 에는 안 넣었다.

TODO 에 적어둔 예상은 이랬다. "큐가 메모리를 먹다가 flow control 이 걸리고, 컨슈머가 밀리면
브로커가 먼저 죽는다." **반만 맞았다.** 메모리는 거의 안 늘었고 브로커도 멀쩡했다.
대신 알람이 걸리는 순간에는 브로커가 아니라 **우리 서비스가 먼저 멈췄다.**

### 컨슈머를 5분 멈췄을 때

geo-indexer 를 끄고 5분 동안 부하를 계속 넣었다. 둘 다 90만 건쯤 밀렸다.

| | 카프카 | 래빗엠큐 |
|---|---|---|
| 브로커 메모리 | 컨테이너 667 → 670MiB | `mem_used` 197 → 265MB |
| 늘어난 디스크 | 54MB | 493MB |
| 메모리, 디스크 알람 | 해당 없음 | 안 걸렸다 |
| 발행하는 쪽 응답 p99 (멈춘 5분 동안) | 3.57ms | 2.08ms |
| 다시 켜고 다 따라잡을 때까지 | 약 53초 (초당 2만 1천 건) | 약 92초 (초당 1만 3천 8백 건) |
| 그동안 레디스에 쓴 가장 오래된 좌표 | **310초 전 것** | **305초 전 것** |
| 순서 뒤집힘 | 0건 | 126만 건 중 2건 |

**메모리가 안 는 건 래빗엠큐 4 라서다.** 4.0 부터 클래식 큐는 메시지를 거의 바로 디스크로
내리고 메모리엔 조금만 쥐고 있다. 예상은 3.x 이전, 메시지를 메모리에 쌓다가 한계에서야
디스크로 내리던 시절 얘기였다. 90만 건이 쌓이는 동안 메모리는 68MB 늘었다.

**대신 디스크를 9배 쓴다.** 메시지 하나에 카프카는 60바이트쯤, 래빗엠큐는 550바이트쯤이다.
본문 JSON 은 130바이트 안팎인데, 카프카는 배치째 lz4 로 압축해서 그보다 작게 들어가고
래빗엠큐는 메시지마다 속성과 색인을 따로 적는다.

**디스크가 찬 다음이 진짜 문제다.** 아래는 잰 게 아니라 위 숫자로 계산한 것이다.
래빗엠큐는 컨슈머가 멈춰 있는 동안 분당 100MB 쯤 쌓이고, 큐에 상한이 없으니 계속 쌓인다.
여유 공간 15.2GB 면 두 시간 반쯤 뒤에 디스크 알람(남은 공간 50MB)이 걸린다. 디스크 알람은
**큐 하나가 아니라 브로커 전체**에 걸린다. 같은 브로커에 있는 `dispatch.x` 도 발행이 막혀서
배차 제안까지 멈춘다. 위치 컨슈머 하나가 죽었는데 배차가 서는 거다.
카프카는 보존 기간(30분)이 지난 세그먼트를 지우니까 330MB 쯤에서 더 안 늘어난다.

**밀린 걸 전부 다시 읽는 건 카프카도 똑같았다.** 따라잡는 1분 동안 5분 묵은 좌표를 레디스에
썼다. 라이더들이 지도 위에서 5분 전 자리부터 지금 자리까지 빨리감기로 다시 지나간 셈이다.
geo-indexer 에 `auto-offset-reset: latest # 밀렸으면 버리고 현재부터` 라고 적어뒀는데,
이 설정은 **커밋된 오프셋이 아예 없을 때만** 먹는다. 한 번이라도 커밋한 그룹은 재시작하면
마지막으로 커밋한 자리부터 읽는다. 주석이 말한 일은 실제로 안 일어나고 있었다. main 에서 고친다.

### 알람이 걸렸을 때 — 발행하는 쪽이 먼저 멈춘다

위에서는 알람이 안 걸렸다. 그래도 디스크가 차거나 다른 큐 때문에 알람이 걸리는 날은 온다.
그날 location-ingest 가 어떻게 되는지 보려고, 부하를 건 채 메모리 알람 기준을 지금 쓰는 양보다
낮게(100MiB) 내려서 억지로 알람을 걸었다가 32초 뒤에 풀었다.

- **알람을 건 뒤 12초 동안은 평소처럼 202 가 나갔다.** 브로커가 소켓을 안 읽어도 그 사이
  좌표가 소켓 버퍼와 도커 데스크톱 포트 포워딩 쪽에 쌓인다(12초 × 초당 3000건, 3만 6천 건쯤).
  이 동안엔 아무도 이상한 걸 모른다.
- **그다음부터 톰캣 스레드 200개가 전부 묶였다.** 스레드 덤프를 떠보니 1개는 소켓에 쓰다가
  서 있고, 199개는 `SocketFrameHandler.writeFrame` 의 락 앞에 줄 서 있었다. 채널을 200개로
  늘려놨어도 TCP 연결은 하나라서 쓰기는 연결 단위로 한 줄로 선다. k6 의 VU 300개도 28초째부터
  전부 응답을 기다리느라 묶였다.
- **실패로 세지도 않았다.** 32초 동안 k6 에서 600건이 10초 타임아웃으로 실패했고 6만 2천 건은
  보내지도 못했다. 그런데 `location_ingest_publish_failed_total` 은 0 이다. `send()` 가 예외를
  안 던지고 그냥 멈추니까 실패한 줄도 모른다. 스레드가 다 묶였으니 헬스체크를 받을 스레드도 없다.
- **풀리고 나니 순서가 1만 5천 건 뒤집혔다.** 알람이 풀린 뒤 geo-indexer 에서 순서 뒤집힘이
  0 에서 15,536 으로 뛰었고 32.7초 묵은 좌표가 들어왔다. 199개 스레드가 기다린 순서대로 나가는
  게 아니라 먼저 락을 잡은 스레드가 먼저 쓴다. 같은 라이더의 1초 간격 좌표 두 개가 거꾸로 들어간다.

카프카 프로듀서는 같은 자리에 상한이 있다. LI-01 때 `max.block.ms` 500ms, `delivery.timeout.ms`
3초로 정해뒀다. 브로커가 못 받으면 3초 안에 버리고 실패 지표를 올린다. 래빗엠큐 쪽에서 이걸
하려면 연결이 막혔다는 알림(`connection.blocked`)을 받아서 그동안 발행을 건너뛰는 코드를
직접 짜야 한다. 이번 실험에선 안 짰다.

### 순서

평소 부하에서는 둘 다 0건이었다. 래빗엠큐도 컨슈머가 멈췄다 따라잡는 동안 126만 건 중 2건뿐이었다.
라이더 한 명의 좌표가 큐에서 3000건 간격으로 떨어져 있고, 컨슈머 셋이 동시에 쥐고 있는 건
1500건(prefetch 500 × 3)이라 같은 라이더 좌표 두 개가 동시에 처리되는 일이 드물어서다.
라이더가 적거나 좌표를 더 자주 보내서 이 간격이 1500건보다 좁아지면 늘어날 거다(안 재봤다).
알람이 풀릴 때처럼 발행하는 쪽에서 섞이면 컨슈머 수와 상관없이 크게 뒤집힌다.

카프카는 파티션 키가 riderId 라서 한 라이더 좌표는 늘 같은 파티션, 같은 스레드로 간다. 래빗엠큐로
같은 걸 하려면 컨슈머를 하나로 줄이거나(single active consumer, 그러면 늘릴 수가 없다) 일관 해시
익스체인지로 큐를 여러 개로 쪼개야 한다. 쪼개는 건 파티션을 손으로 만드는 거다.

### TTL — 래빗엠큐가 나은 것

큐에 `x-message-ttl` 5초를 걸고 컨슈머를 2분 멈췄다.

| | TTL 없음 (5분 정지) | TTL 5초 (2분 정지) |
|---|---|---|
| 큐 깊이 | 91만 건까지 계속 늘었다 | 1만 5천 건에서 멈췄다 (5초 × 초당 3000건) |
| 다시 켠 뒤 가장 오래된 좌표 | 305초 전 것 | 5.2초 전 것 |
| 다 따라잡을 때까지 | 약 92초 | 20초 안 |

브로커가 5초 넘은 좌표를 알아서 버려준다. 위치처럼 "묵으면 쓸모없는" 데이터에 딱 맞는 기능이다.
카프카에는 메시지마다 유효기간을 거는 기능이 없다. 보존 기간은 세그먼트 단위라 분 단위로만 지운다.
카프카로 같은 효과를 내려면 컨슈머가 sentAt 을 보고 오래된 건 건너뛰게 짜야 한다.

### 평소 부하 (컨슈머가 잘 따라올 때)

초당 3000건을 60초 넣었을 때 둘 다 문제없었다. 발행 응답 p99 는 카프카 44.7ms, 래빗엠큐 17.0ms 로
나왔는데, k6 와 JVM 둘, 도커가 같은 노트북 CPU 를 나눠 써서 흔들리는 값이다. 위 표의 멈춘 5분
구간에선 2~4ms 로 비슷했다. 좌표가 레디스까지 가는 시간 중앙값은 카프카 15ms, 래빗엠큐 36ms 인데
래빗엠큐 쪽은 배치를 50ms 까지 모으게 해둔 몫이다.

### 그래서 어느 쪽을 쓰나

**카프카를 그대로 둔다.** 이유는 세 가지다.
