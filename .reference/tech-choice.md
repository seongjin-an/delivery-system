# 기술 선택 근거

같은 일을 다른 방법으로도 해보고, 그 결과를 여기 표로 남긴다.
읽어서 아는 것과 겪어서 아는 것의 차이를 기록으로 남기는 게 목적이다.

측정은 전부 같은 노트북, 같은 도커 컴포즈, 같은 부하(주문 100건을 order-api 두 대에
번갈아 넣기)로 했다.

---

## 1. 아웃박스를 카프카로 내보내는 방법 — 폴러 vs Debezium CDC

주문 행과 이벤트 행을 한 트랜잭션에 넣는 것(아웃박스 패턴)까지는 같다.
다른 건 **그 이벤트 행을 누가 카프카로 옮기느냐**다.

| | 폴러 (OR-06) | Debezium CDC |
|---|---|---|
| 옮기는 주체 | 앱 안의 스케줄러 | 카프카 커넥트 (별도 프로세스) |
| 읽는 곳 | `outbox` 테이블 | MySQL binlog |
| 인스턴스 여러 대 | `FOR UPDATE SKIP LOCKED` 로 나눠 집는다 | 커넥터가 한 곳이라 신경 쓸 게 없다 |
| DB 부하 | 200ms 마다 SELECT + UPDATE | 없다 (binlog 를 따로 읽는다) |
| 필요한 인프라 | 없다 | 커넥트 컨테이너 + 복제 권한 |

### 지연 (아웃박스 INSERT → 카프카 발행)

| | 최소 | 중앙값 | 평균 | p95 | 최대 |
|---|---|---|---|---|---|
| 폴러 | 58ms | — | **297ms** | — | 901ms |
| CDC | 5ms | 16ms | **33ms** | 140ms | 143ms |

평균이 9배 차이 난다. 폴러가 느린 건 코드가 나빠서가 아니라 **구조가 그렇게 생겨서**다.
주기가 200ms 면 방금 들어온 행은 평균 100ms 를 그냥 기다린다. 거기에 한 배치(100건)에
다 안 들어간 것들이 다음 주기로 밀리면서 꼬리가 길어진다. 최대 901ms 가 그 꼬리다.

CDC 는 기다리는 구간 자체가 없다. binlog 에 적히는 순간 읽어간다. 중앙값 16ms 는
사실상 "MySQL 이 커밋하고 커넥트가 카프카에 쓰는 시간" 이다.

### 그럼 폴러는 왜 먼저 만들었나

`SKIP LOCKED` 를 직접 겪어보려고 그랬다. 세션 두 개로 재본 결과가 이렇다.

| 쿼리 | 응답까지 | 받아간 행 |
|---|---|---|
| `FOR UPDATE SKIP LOCKED` | 275ms | 114, 115, 116 (다른 행) |
| `FOR UPDATE` 만 | 3787ms | 111, 112, 113 (**같은 행**) |

`SKIP LOCKED` 를 빼면 두 겹으로 깨진다. 뒤에 온 인스턴스가 앞사람을 기다리느라 늘린 의미가
없어지고, 기다린 끝에 받는 게 앞사람이 방금 발행한 그 행이라 카프카에 중복이 나간다.

CDC 로 가면 이 문제 자체가 사라진다. 사라지는 게 아니라 **커넥트 쪽으로 옮겨간다** —
커넥터를 두 개 띄우면 같은 binlog 를 두 번 읽어서 똑같이 중복이 난다. 다만 커넥트는
"커넥터 하나에 태스크 하나" 가 기본이라 우리가 실수하기 어려울 뿐이다.

### 대가

공짜는 아니다.

- **컨테이너가 하나 늘었다.** 메모리를 1GB 쯤 더 쓴다.
- **장애가 앱 밖으로 나갔다.** 이벤트가 안 나갈 때 앱 로그를 봐도 아무것도 없다.
  `curl localhost:8083/connectors/order-outbox-connector/status` 를 봐야 한다.
- **커넥터가 안 떠 있으면 이벤트가 한 건도 안 나간다.** 폴러 때는 앱만 살아 있으면 됐다.
  `scripts/start.sh` 가 등록까지 해주지만, 인프라를 부분만 띄우면 조용히 멈춘다.
- **처음 붙일 때 기존 행은 안 읽는다** (`snapshot.mode=schema_only`). 우리는 폴러가 이미
  내보낸 것들이라 이게 맞는 선택이지만, 처음부터 CDC 로 시작한다면 `initial` 이어야 한다.

### 겪은 것

**커넥터가 RUNNING 인데 이벤트가 한 건도 안 나갔다.** 상태만 보면 멀쩡했다.
커넥트 로그를 보니 `delivery` 라는 토픽에 계속 쓰려다 실패하고 있었다.

```
Error while fetching metadata ... {delivery=UNKNOWN_TOPIC_OR_PARTITION}
```

Debezium MySQL 커넥터는 DDL 변경 이벤트를 `topic.prefix` 와 같은 이름의 토픽에 쓴다.
우리는 파티션 수를 못 박으려고 브로커의 auto-create 를 꺼놨으니 그 토픽이 없고,
커넥터는 거기서 막힌 채 아웃박스 이벤트를 하나도 못 내보냈다.
`include.schema.changes=false` 로 껐다.

교훈은 "커넥터 상태가 RUNNING 이라고 일이 되고 있는 게 아니다" 다.
태스크는 살아 있어도 프로듀서가 못 쓰고 있을 수 있다.

### 그래서 어느 쪽을 쓰나

**CDC 를 기본으로 둔다** (`delivery.outbox.mode=CDC`).
폴러 코드는 지우지 않고 `mode=POLLER` 뒤에 남겨뒀다. 같은 조건에서 다시 재보려면 필요하고,
커넥트 없이 앱만 띄우고 싶을 때도 쓸 수 있다.
