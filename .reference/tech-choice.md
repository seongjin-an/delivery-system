# 기술 선택 근거

같은 일을 다른 방법으로도 해보고, 그 결과를 여기 표로 남긴다.
읽어서 아는 것과 겪어서 아는 것의 차이를 기록으로 남기는 게 목적이다.

측정은 전부 같은 노트북(8코어, 16GB)과 같은 도커 컴포즈로 했다. 부하는 절마다 다르니
각 절 첫머리에 적는다.

---

## 1. 아웃박스를 카프카로 내보내는 방법 — 폴러 vs Debezium CDC

부하: 주문 100건을 order-api 두 대에 번갈아 넣었다.

주문 행과 이벤트 행을 한 트랜잭션에 넣는 것(아웃박스 패턴)까지는 같다.
다른 건 **그 이벤트 행을 누가 카프카로 옮기느냐**다.

| | 폴러 (OR-06) | Debezium CDC |
|---|---|---|
| 옮기는 주체 | 앱 안의 스케줄러 | 카프카 커넥트 (별도 프로세스) |
| 읽는 곳 | `outbox` 테이블 | MySQL binlog |
| 인스턴스 여러 대 | `FOR UPDATE SKIP LOCKED` 로 나눠 집는다 | 커넥터가 한 곳이라 신경 쓸 게 없다 |
| DB 부하 | 200ms 마다 SELECT + UPDATE | 없다 (binlog 를 따로 읽는다) |
| 필요한 인프라 | 없다 | 커넥트 컨테이너 + 복제 권한 |

### 지연 (아웃박스 INSERT → 카프카 발행)

| | 최소 | 중앙값 | 평균 | p95 | 최대 |
|---|---|---|---|---|---|
| 폴러 | 58ms | — | **297ms** | — | 901ms |
| CDC | 5ms | 16ms | **33ms** | 140ms | 143ms |

평균이 9배 차이 난다. 폴러가 느린 건 코드가 나빠서가 아니라 **구조가 그렇게 생겨서**다.
주기가 200ms 면 방금 들어온 행은 평균 100ms 를 그냥 기다린다. 거기에 한 배치(100건)에
다 안 들어간 것들이 다음 주기로 밀리면서 꼬리가 길어진다. 최대 901ms 가 그 꼬리다.

CDC 는 기다리는 구간 자체가 없다. binlog 에 적히는 순간 읽어간다. 중앙값 16ms 는
사실상 "MySQL 이 커밋하고 커넥트가 카프카에 쓰는 시간" 이다.

### 그럼 폴러는 왜 먼저 만들었나

`SKIP LOCKED` 를 직접 겪어보려고 그랬다. 세션 두 개로 재본 결과가 이렇다.

| 쿼리 | 응답까지 | 받아간 행 |
|---|---|---|
| `FOR UPDATE SKIP LOCKED` | 275ms | 114, 115, 116 (다른 행) |
| `FOR UPDATE` 만 | 3787ms | 111, 112, 113 (**같은 행**) |

`SKIP LOCKED` 를 빼면 두 겹으로 깨진다. 뒤에 온 인스턴스가 앞사람을 기다리느라 늘린 의미가
없어지고, 기다린 끝에 받는 게 앞사람이 방금 발행한 그 행이라 카프카에 중복이 나간다.

CDC 로 가면 이 문제 자체가 사라진다. 사라지는 게 아니라 **커넥트 쪽으로 옮겨간다** —
커넥터를 두 개 띄우면 같은 binlog 를 두 번 읽어서 똑같이 중복이 난다. 다만 커넥트는
"커넥터 하나에 태스크 하나" 가 기본이라 우리가 실수하기 어려울 뿐이다.

### 대가

공짜는 아니다.

- **컨테이너가 하나 늘었다.** 메모리를 1GB 쯤 더 쓴다.
- **장애가 앱 밖으로 나갔다.** 이벤트가 안 나갈 때 앱 로그를 봐도 아무것도 없다.
  `curl localhost:8083/connectors/order-outbox-connector/status` 를 봐야 한다.
- **커넥터가 안 떠 있으면 이벤트가 한 건도 안 나간다.** 폴러 때는 앱만 살아 있으면 됐다.
  `scripts/start.sh` 가 등록까지 해주지만, 인프라를 부분만 띄우면 조용히 멈춘다.
- **처음 붙일 때 기존 행은 안 읽는다** (`snapshot.mode=schema_only`). 우리는 폴러가 이미
  내보낸 것들이라 이게 맞는 선택이지만, 처음부터 CDC 로 시작한다면 `initial` 이어야 한다.

### 겪은 것

**커넥터가 RUNNING 인데 이벤트가 한 건도 안 나갔다.** 상태만 보면 멀쩡했다.
커넥트 로그를 보니 `delivery` 라는 토픽에 계속 쓰려다 실패하고 있었다.

```
Error while fetching metadata ... {delivery=UNKNOWN_TOPIC_OR_PARTITION}
```

Debezium MySQL 커넥터는 DDL 변경 이벤트를 `topic.prefix` 와 같은 이름의 토픽에 쓴다.
우리는 파티션 수를 못 박으려고 브로커의 auto-create 를 꺼놨으니 그 토픽이 없고,
커넥터는 거기서 막힌 채 아웃박스 이벤트를 하나도 못 내보냈다.
`include.schema.changes=false` 로 껐다.

교훈은 "커넥터 상태가 RUNNING 이라고 일이 되고 있는 게 아니다" 다.
태스크는 살아 있어도 프로듀서가 못 쓰고 있을 수 있다.

### 그래서 어느 쪽을 쓰나

**CDC 를 기본으로 둔다** (`delivery.outbox.mode=CDC`).
폴러 코드는 지우지 않고 `mode=POLLER` 뒤에 남겨뒀다. 같은 조건에서 다시 재보려면 필요하고,
커넥트 없이 앱만 띄우고 싶을 때도 쓸 수 있다.

## 2. 위치 스트림 — 카프카 vs 래빗엠큐

부하: k6 로 location-ingest 에 초당 3000건(라이더 3000명이 1초마다). 컨슈머는 둘 다 3개씩,
한 번에 최대 500건씩 받는다. 래빗엠큐 4.3.6 클래식 큐, cp-kafka 7.6.1 단일 브로커.
실험 코드와 측정 원본은 `exp/location-rabbitmq` 브랜치의 `experiments/location-transport/` 에 있다.
main 에는 안 넣었다.

TODO 에 적어둔 예상은 이랬다. "큐가 메모리를 먹다가 flow control 이 걸리고, 컨슈머가 밀리면
브로커가 먼저 죽는다." **반만 맞았다.** 메모리는 거의 안 늘었고 브로커도 멀쩡했다.
대신 알람이 걸리는 순간에는 브로커가 아니라 **우리 서비스가 먼저 멈췄다.**

### 컨슈머를 5분 멈췄을 때

geo-indexer 를 끄고 5분 동안 부하를 계속 넣었다. 둘 다 90만 건쯤 밀렸다.

| | 카프카 | 래빗엠큐 |
|---|---|---|
| 브로커 메모리 | 컨테이너 667 → 670MiB | `mem_used` 197 → 265MB |
| 늘어난 디스크 | 54MB | 493MB |
| 메모리, 디스크 알람 | 해당 없음 | 안 걸렸다 |
| 발행하는 쪽 응답 p99 (멈춘 5분 동안) | 3.57ms | 2.08ms |
| 다시 켜고 다 따라잡을 때까지 | 약 53초 (초당 2만 1천 건) | 약 92초 (초당 1만 3천 8백 건) |
| 그동안 레디스에 쓴 가장 오래된 좌표 | **310초 전 것** | **305초 전 것** |
| 순서 뒤집힘 | 0건 | 126만 건 중 2건 |

**메모리가 안 는 건 래빗엠큐 4 라서다.** 4.0 부터 클래식 큐는 메시지를 거의 바로 디스크로
내리고 메모리엔 조금만 쥐고 있다. 예상은 3.x 이전, 메시지를 메모리에 쌓다가 한계에서야
디스크로 내리던 시절 얘기였다. 90만 건이 쌓이는 동안 메모리는 68MB 늘었다.

**대신 디스크를 9배 쓴다.** 메시지 하나에 카프카는 60바이트쯤, 래빗엠큐는 550바이트쯤이다.
본문 JSON 은 130바이트 안팎인데, 카프카는 배치째 lz4 로 압축해서 그보다 작게 들어가고
래빗엠큐는 메시지마다 속성과 색인을 따로 적는다.

**디스크가 찬 다음이 진짜 문제다.** 아래는 잰 게 아니라 위 숫자로 계산한 것이다.
래빗엠큐는 컨슈머가 멈춰 있는 동안 분당 100MB 쯤 쌓이고, 큐에 상한이 없으니 계속 쌓인다.
여유 공간 15.2GB 면 두 시간 반쯤 뒤에 디스크 알람(남은 공간 50MB)이 걸린다. 디스크 알람은
**큐 하나가 아니라 브로커 전체**에 걸린다. 같은 브로커에 있는 `dispatch.x` 도 발행이 막혀서
배차 제안까지 멈춘다. 위치 컨슈머 하나가 죽었는데 배차가 서는 거다.
카프카는 보존 기간(30분)이 지난 세그먼트를 지우니까 330MB 쯤에서 더 안 늘어난다.

**밀린 걸 전부 다시 읽는 건 카프카도 똑같았다.** 따라잡는 1분 동안 5분 묵은 좌표를 레디스에
썼다. 라이더들이 지도 위에서 5분 전 자리부터 지금 자리까지 빨리감기로 다시 지나간 셈이다.
geo-indexer 에 `auto-offset-reset: latest # 밀렸으면 버리고 현재부터` 라고 적어뒀는데,
이 설정은 **커밋된 오프셋이 아예 없을 때만** 먹는다. 한 번이라도 커밋한 그룹은 재시작하면
마지막으로 커밋한 자리부터 읽는다. 주석이 말한 일은 실제로 안 일어나고 있었다. main 에서 고친다.

### 알람이 걸렸을 때 — 발행하는 쪽이 먼저 멈춘다

위에서는 알람이 안 걸렸다. 그래도 디스크가 차거나 다른 큐 때문에 알람이 걸리는 날은 온다.
그날 location-ingest 가 어떻게 되는지 보려고, 부하를 건 채 메모리 알람 기준을 지금 쓰는 양보다
낮게(100MiB) 내려서 억지로 알람을 걸었다가 32초 뒤에 풀었다.

- **알람을 건 뒤 12초 동안은 평소처럼 202 가 나갔다.** 브로커가 소켓을 안 읽어도 그 사이
  좌표가 소켓 버퍼와 도커 데스크톱 포트 포워딩 쪽에 쌓인다(12초 × 초당 3000건, 3만 6천 건쯤).
  이 동안엔 아무도 이상한 걸 모른다.
- **그다음부터 톰캣 스레드 200개가 전부 묶였다.** 스레드 덤프를 떠보니 1개는 소켓에 쓰다가
  서 있고, 199개는 `SocketFrameHandler.writeFrame` 의 락 앞에 줄 서 있었다. 채널을 200개로
  늘려놨어도 TCP 연결은 하나라서 쓰기는 연결 단위로 한 줄로 선다. k6 의 VU 300개도 28초째부터
  전부 응답을 기다리느라 묶였다.
- **실패로 세지도 않았다.** 32초 동안 k6 에서 600건이 10초 타임아웃으로 실패했고 6만 2천 건은
  보내지도 못했다. 그런데 `location_ingest_publish_failed_total` 은 0 이다. `send()` 가 예외를
  안 던지고 그냥 멈추니까 실패한 줄도 모른다. 스레드가 다 묶였으니 헬스체크를 받을 스레드도 없다.
- **풀리고 나니 순서가 1만 5천 건 뒤집혔다.** 알람이 풀린 뒤 geo-indexer 에서 순서 뒤집힘이
  0 에서 15,536 으로 뛰었고 32.7초 묵은 좌표가 들어왔다. 199개 스레드가 기다린 순서대로 나가는
  게 아니라 먼저 락을 잡은 스레드가 먼저 쓴다. 같은 라이더의 1초 간격 좌표 두 개가 거꾸로 들어간다.

카프카 프로듀서는 같은 자리에 상한이 있다. LI-01 때 `max.block.ms` 500ms, `delivery.timeout.ms`
3초로 정해뒀다. 브로커가 못 받으면 3초 안에 버리고 실패 지표를 올린다. 래빗엠큐 쪽에서 이걸
하려면 연결이 막혔다는 알림(`connection.blocked`)을 받아서 그동안 발행을 건너뛰는 코드를
직접 짜야 한다. 이번 실험에선 안 짰다.

### 순서

평소 부하에서는 둘 다 0건이었다. 래빗엠큐도 컨슈머가 멈췄다 따라잡는 동안 126만 건 중 2건뿐이었다.
라이더 한 명의 좌표가 큐에서 3000건 간격으로 떨어져 있고, 컨슈머 셋이 동시에 쥐고 있는 건
1500건(prefetch 500 × 3)이라 같은 라이더 좌표 두 개가 동시에 처리되는 일이 드물어서다.
라이더가 적거나 좌표를 더 자주 보내서 이 간격이 1500건보다 좁아지면 늘어날 거다(안 재봤다).
알람이 풀릴 때처럼 발행하는 쪽에서 섞이면 컨슈머 수와 상관없이 크게 뒤집힌다.

카프카는 파티션 키가 riderId 라서 한 라이더 좌표는 늘 같은 파티션, 같은 스레드로 간다. 래빗엠큐로
같은 걸 하려면 컨슈머를 하나로 줄이거나(single active consumer, 그러면 늘릴 수가 없다) 일관 해시
익스체인지로 큐를 여러 개로 쪼개야 한다. 쪼개는 건 파티션을 손으로 만드는 거다.

### TTL — 래빗엠큐가 나은 것

큐에 `x-message-ttl` 5초를 걸고 컨슈머를 2분 멈췄다.

| | TTL 없음 (5분 정지) | TTL 5초 (2분 정지) |
|---|---|---|
| 큐 깊이 | 91만 건까지 계속 늘었다 | 1만 5천 건에서 멈췄다 (5초 × 초당 3000건) |
| 다시 켠 뒤 가장 오래된 좌표 | 305초 전 것 | 5.2초 전 것 |
| 다 따라잡을 때까지 | 약 92초 | 20초 안 |

브로커가 5초 넘은 좌표를 알아서 버려준다. 위치처럼 "묵으면 쓸모없는" 데이터에 딱 맞는 기능이다.
카프카에는 메시지마다 유효기간을 거는 기능이 없다. 보존 기간은 세그먼트 단위라 분 단위로만 지운다.
카프카로 같은 효과를 내려면 컨슈머가 sentAt 을 보고 오래된 건 건너뛰게 짜야 한다.

### 평소 부하 (컨슈머가 잘 따라올 때)

초당 3000건을 60초 넣었을 때 둘 다 문제없었다. 발행 응답 p99 는 카프카 44.7ms, 래빗엠큐 17.0ms 로
나왔는데, k6 와 JVM 둘, 도커가 같은 노트북 CPU 를 나눠 써서 흔들리는 값이다. 위 표의 멈춘 5분
구간에선 2~4ms 로 비슷했다. 좌표가 레디스까지 가는 시간 중앙값은 카프카 15ms, 래빗엠큐 36ms 인데
래빗엠큐 쪽은 배치를 50ms 까지 모으게 해둔 몫이다.

### 그래서 어느 쪽을 쓰나

**카프카를 그대로 둔다.** 이유는 세 가지다.

1. 밀려도 디스크를 9분의 1만 쓰고, 보존 기간이 넘치지 않게 막아준다. 래빗엠큐는 막아주는 게 없어서
   결국 디스크 알람이 걸리고, 그러면 같은 브로커의 배차 제안까지 멈춘다.
2. 브로커가 못 받을 때 발행하는 쪽이 3초 안에 포기한다. 래빗엠큐는 톰캣 스레드가 다 묶이고,
   실패 지표도 안 올라가서 모른다.
3. 라이더별 순서를 따로 신경 쓸 필요가 없다.

래빗엠큐에서 가져올 것도 하나 있다. **묵은 좌표는 버린다.** 카프카엔 TTL 이 없으니 geo-indexer 가
sentAt 을 보고 오래된 좌표를 건너뛰게 만든다(`TODO.md` geo-indexer 절).

## 3. 배차 제안 — 래빗엠큐 vs 카프카

부하: 시뮬레이터로 라이더 1000명, 주문 초당 10건을 60초 동안 넣었다. 수락도 거절도 안 하게 둬서 모든 제안이
10초 타이머로만 끝난다. 주문 하나가 10초 간격으로 다섯 번 돌고 실패로 끝나니까 한 판에 재제안이 2800건쯤 나온다.
판마다 JVM 을 한 번 데운 뒤에 쟀다. 실험 코드와 측정 원본은 `exp/offer-kafka` 브랜치의
`experiments/offer-transport/` 에 있다.

TODO 에 적어둔 예상은 이랬다. "'이 라이더에게만, 10초 TTL' 을 표현할 방법이 없다. 스케줄러 테이블을 따로 만들게 되는데
그게 곧 TTL+DLX 를 손으로 재구현하는 것이다." **틀렸다.** 스케줄러 테이블 없이 컨슈머 하나로 됐다.
그래도 래빗엠큐를 그대로 둔다. 다만 이유가 바뀌었다.

### 카프카로 만든 타이머

제안을 `dispatch.offer` 토픽에 한 번 넣고, 컨슈머 그룹 둘이 각자 읽는다. notification-worker 는 알림을 보내려고,
offer-relay 의 타이머는 10초를 세려고 읽는다. 래빗엠큐에서 익스체인지가 알림 큐와 타이머 큐로 복사해주던 걸
그룹 두 개가 대신하는 거다.

타이머는 레코드를 하나 꺼낼 때마다 `offeredAt + 10초` 가 될 때까지 자다가 `dispatch.offer.expired` 로 넘기고 커밋한다.
이게 되는 건 TTL 이 전부 10초라서다. 한 파티션 안에서는 먼저 온 제안이 먼저 만료되니까 맨 앞 하나만 기다리면 되고,
그동안 뒤엣것들도 거의 다 제 차례가 된다. 자는 스레드는 제안 수가 아니라 파티션 수(6개)만큼이다.
코드는 주석을 빼면 44줄이었다.

"이 라이더에게만" 도 문제가 아니었다. 라이더 폰으로는 notification-worker 가 HTTP 로 쏜다. 래빗엠큐에서도 라이더마다
큐가 있는 게 아니고 메시지 안의 riderId 를 보고 워커가 보낸다. 브로커가 사람을 골라주는 일은 원래 없었다.

### 10초 타이머가 실제로 몇 초에 울렸나

제안이 나간 시각(offeredAt)부터 offer-relay 에 만료 메시지가 닿을 때까지다.

| | 래빗엠큐, 만료 컨슈머 1개 (main 기본) | 래빗엠큐, 컨슈머 6개 | 카프카, 파티션 6개 |
|---|---|---|---|
| 잰 건수 | 2767 | 2825 | 2815 |
| 10.1초 안에 온 비율 | 79.9% | 99.5% | 91.7% |
| p95 | 11.2초 | 10.1초 안 | 10.25초 |
| p99 | 11.8초 | 10.1초 안 | 10.9초 |
| 가장 늦은 것 | 12초 안 | 10.5초 안 | 12초 안 |

컨슈머 수를 맞추면 래빗엠큐가 조금 더 정확하다. 카프카 쪽은 파티션마다 스레드 하나가 자고, 깨고, 만료 토픽에 넣고
ack 를 기다리는 걸 순서대로 하니까 그만큼 밀린다. 그래도 라이더 입장에서 0.8초는 차이가 안 난다.

main 기본값(만료 컨슈머 1개)도 초당 주문 10건에서는 괜찮았다. 전부 12초 안에 왔다. 한 가지 조심할 건 **막 재시작한
직후**다. 지표를 비우려고 offer-relay 를 재시작한 채로 첫 판을 돌렸더니, JVM 이 식어 있는 첫 30초 동안 재제안을 초당
1~9건밖에 못 해서(데워진 뒤엔 40~78건) p95 가 24초까지 늘었다. 점심 피크에 배포하면 이게 그대로 나온다.

### 타이머를 쥔 프로세스가 죽으면

같은 부하에서 25초째 offer-relay 를 `kill -9` 로 죽이고 20초 뒤에 다시 띄웠다.

| | 래빗엠큐 (컨슈머 6개) | 카프카 |
|---|---|---|
| 꺼져 있던 시간 | 28초 | 31초 |
| 30초 안에 온 비율 | 90.2% | 79.5% |
| p95 / p99 | 44.7초 / 57.0초 | 52.7초 / 58.5초 |
| 배차 중에 멈춘 주문 | 0 / 601건 | 0 / 600건 |

**둘 다 주문을 잃지 않았다.** 래빗엠큐는 타이머가 브로커 안에 있어서 offer-relay 가 없는 동안에도 10초가 흐르고,
만료된 건 만료 큐에서 기다린다. 카프카는 넘긴 다음에 커밋하니까 자던 레코드는 커밋이 안 된 채라 다시 뜬 쪽이 다시 읽는다.
문서에 "재시작하면 자던 스레드가 날아간다" 고 적어뒀던 건 제안마다 스레드를 재울 때 얘기였다.

**차이는 다시 일을 받기까지 걸린 시간이다.** 카프카 쪽 offer-relay 는 18:40:17 에 다시 떴는데 파티션은 18:40:31 에야
받았다. 죽인 시각(18:39:46)으로부터 딱 45초, 컨슈머의 `session.timeout.ms` 기본값이다. `kill -9` 로 죽은 컨슈머는
"나간다" 는 말을 못 하고 가니까, 브로커는 하트비트가 45초 동안 끊긴 걸 보고서야 죽었다고 판정하고 파티션을 다시 나눈다.
그 전까지는 새로 뜬 인스턴스도 놀고 있다. 래빗엠큐는 TCP 연결이 끊기는 순간 ack 안 된 메시지를 큐로 되돌린다.

### 마케팅 1만 건 뒤에 제안 하나

가게 근처에 라이더 100명(전원 즉시 수락)을 띄우고, 마케팅 푸시 1만 건을 넣은 직후 주문 하나를 넣었다.
외부 푸시 한도는 초당 200건, 한 건 보내는 데 120ms 다. 판마다 밀린 마케팅은 비우고 시작했다.

| | 배차까지 | 몇 번째 제안에서 | 제안이 나가고 푸시가 나가기까지 |
|---|---|---|---|
| 래빗엠큐, prefetch 250 (main 기본) | 52.5초에 FAILED (1판) | 다섯 번 다 만료 | 한 번도 못 나감 |
| 래빗엠큐, prefetch 20 (3판) | 6.5 / 5.3 / 6.1초 | 첫 번째 | 2.8 / 2.6 / 2.7초 |
| 카프카, 마케팅과 한 토픽 (3판) | 55.9초에 FAILED / 34.2 / 24.2초 | 다섯 번 다 만료 / 네 번째 / 세 번째 | 나간 것만 0.45 / 0.26초 |
| 카프카, 제안 전용 토픽 (3판) | 3.2 / 3.0 / 4.0초 | 첫 번째 | 0.29 / 0.15 / 0.15초 |

카프카엔 우선순위가 없어서 한 토픽에 섞으면 제안이 마케팅 뒤에 줄을 선다(1만 건을 16 파티션으로 나누면 한 파티션에 600건쯤이다). 운 좋게 덜 막힌
파티션에 떨어진 제안만 나갔다. 그런데 **제안만 받는 토픽과 컨슈머를 따로 두니 래빗엠큐 우선순위 큐보다 빨랐다.**
래빗엠큐는 priority 9 로 큐 안에서는 앞지르지만, 컨슈머들이 이미 쥐고 있는 마케팅(prefetch 20개씩) 뒤에서 2.6~2.8초를
기다린다. 전용 줄은 앞에 기다릴 게 아예 없다. 한도(토큰)는 마케팅과 같이 나눠 쓰는데도 한 번도 안 걸렸다.

여기서 배운 건 브로커 차이가 아니다. **우선순위 큐보다 줄을 따로 세우는 게 낫다.** 래빗엠큐에서도 제안을 별도 큐로
빼면 같은 효과가 날 거다(안 재봤다).

### 그래서 어느 쪽을 쓰나

**래빗엠큐를 그대로 둔다.** 다만 "카프카로는 못 만든다" 가 이유가 아니다. 이유는 세 가지다.

1. **타이머가 코드가 아니라 설정이다.** 카프카 타이머 44줄은 TTL 이 하나일 때만 이렇게 간단하다. 두 번째 제안부터는
   15초 식으로 TTL 이 갈리면 맨 앞의 긴 것 뒤에서 짧은 것들이 늦어져서 TTL 마다 토픽을 따로 둬야 한다.
   래빗엠큐는 큐를 하나 더 선언하면 된다.
2. **죽었을 때 바로 되돌린다.** 카프카는 45초 동안 아무도 만료를 처리하지 않는다. `session.timeout.ms` 를 줄이면
   되지만, 그만큼 GC 한 번 길게 멈춘 멀쩡한 컨슈머도 쫓겨나서 리밸런싱이 잦아진다.
3. **컨슈머 수를 맞추면 조금 더 정확하다** (p99 10.1초 안 대 10.9초).

카프카에서 가져올 것도 하나 있다. **제안 푸시를 마케팅과 다른 줄에 세운다.** 지금 main 은 prefetch 250 이 기본이라
마케팅 1만 건이면 제안이 한 건도 못 나간다. 제안 전용 큐를 따로 두는 걸 `TODO.md` notification-worker 절에 적었다.

## 4. 후보 검색 — 레디스 GEO vs MySQL 공간 인덱스

부하: 라이더 1만 명이 3초마다 좌표를 보낸다(초당 3333건). 후보 검색은 주문을 거치지 않고 dispatch-engine 의
`CandidateFinder` 를 그대로 부르는 실험용 엔드포인트를 k6 로 초당 50, 200, 500, 1000건씩 30초 동안 불렀다.
주문을 초당 200건 흘리면 order-api 쓰기와 Debezium, 카프카까지 전부 섞여서 뭘 재는지 흐려지기 때문이다.
실험 코드와 측정 원본은 `exp/geo-mysql` 브랜치의 `experiments/geo-mysql/` 에 있다.

바꾼 건 "가까운 30명" 을 찾는 단계 하나다. 그 30명이 IDLE 인지는 두 경우 다 레디스 `rider:state` 에서 읽는다.
MySQL 쪽도 제대로 짰다. `POINT SRID 4326` 컬럼에 공간 인덱스를 걸고, 반경을 감싸는 네모로 인덱스를 먼저 탄 다음
(`MBRContains`, EXPLAIN 으로 인덱스 range 스캔 확인) 남은 것만 `ST_Distance_Sphere` 로 정렬해 30명을 자른다.

TODO 에 적어둔 예상은 "주문 하나당 쿼리 하나라서 초당 200 주문이면 DB 가 먼저 눕는다" 였다. **맞았는데, 더 일찍 누웠다.**
그리고 읽기보다 좌표 쓰기가 먼저 문제였다.

### 좌표 쓰기가 먼저 막힌다

MySQL 로 후보를 찾으려면 좌표가 MySQL 에 있어야 한다. geo-indexer 가 레디스에 쓴 뒤 같은 배치를 MySQL 에도
upsert 하게 했다(`rewriteBatchedStatements` 로 배치 하나를 문장 하나로 보낸다).

| | 레디스만 | 레디스 + MySQL |
|---|---|---|
| 카프카 랙 | 800건 아래 | 28,000건에서 안 줄어듦 |
| 10초 넘게 묵어서 버린 좌표 | 90초 동안 0건 | 3분쯤에 17,490건, 계속 늘어남 |

레디스 + MySQL 판에서 배치(평균 500건) 하나에 레디스 쓰기가 평균 179ms, MySQL upsert 가 평균 321ms(p99 670ms)
걸렸고, 그때 MySQL CPU 는 98%, 레디스는 31% 였다. 컨슈머 셋이 배치 하나에 0.5초씩 쓰면 초당 3000건이 한계라
들어오는 3333건을 못 따라간다. 레디스만 쓰는 판은 JVM 을 데운 뒤 90초를 쟀다(갓 띄운 채로는 1분쯤 랙이 쌓였다가 따라잡았다).
MySQL 판이 끝없이 밀리지 않고 버틴 건 "10초 넘은 좌표는 버린다"(geo-indexer max-age, PR #21) 덕분이다.

### 검색 — 쓰기가 없을 때

좌표 쓰기를 끄고 검색만 불렀다.

| 검색 초당 | 레디스 p50 / p99 | MySQL p50 / p99 |
|---|---|---|
| 50 | 6.4ms / 23ms | 28ms / 52ms |
| 200 | 3.1ms / 20ms | **초당 171건이 한계**, 1.52s / 2.75s |
| 500 | 3.4ms / 71ms | 초당 161건, 2.38s / 3.57s |
| 1000 | 초당 915건, 127ms / 1.91s (풀 켠 뒤) | 초당 173건, 2.22s / 3.13s |

MySQL 은 초당 170건 근처에서 멈췄고 그때 CPU 가 430~530% 였다. 검색 하나에 CPU 를 30ms 쯤 쓴다.
반경 3km 를 감싸는 네모(6km × 6km) 안에 라이더가 900명쯤 들어오는데(1만 명을 뿌린 넓이로 나눈 계산이다),
그 900명 전부의 거리를 계산하고 정렬한 뒤 30명을 자르기 때문이다. 레디스 `GEOSEARCH ... ASC COUNT 30` 은 가까운 칸부터 세다가 30명에서 멈춘다.
레디스의 초당 1000건 한계는 레디스가 아니라 노트북이었다(레디스 CPU 79%, k6 와 JVM 셋이 같이 돈다).

### 검색 — 좌표 쓰기가 켜져 있을 때 (실제 상황)

| 검색 초당 | 레디스 p50 / p99 | MySQL p50 / p99 |
|---|---|---|
| 50 | 15ms / 1.01s (재시작 직후 워밍업) | 426ms / 1.15s |
| 200 | 37ms / 267ms | **초당 48건이 한계**, 7.9s / 10s(타임아웃 1.6%) |
| 500 | 초당 364건, 906ms / 1.86s | 초당 47건, 8.3s / 10s |

좌표 쓰기가 붙으니 MySQL 검색 한계가 초당 170건에서 48건으로 떨어졌다. 서버 안에서 쿼리만 떼어 봐도 초당 50건에서
p50 이 24ms 에서 402ms 로 17배 느려졌다. 초당 3333건의 upsert 가 공간 인덱스(R-tree)를 계속 고치는 동안 같은 인덱스를
읽어야 하니 쓰기와 읽기가 같은 페이지를 두고 다투는 걸로 보인다(락 대기까지 떠보지는 않았다). 레디스 쪽이 초당 364건에서 막힌 건 아래 "같이 찾은 것" 의
연결 문제가 섞여 있어서다(이 판은 풀을 켜기 전에 쟀다).

### 같이 찾은 것 두 개

**dispatch-engine 이 검색마다 레디스 연결을 새로 열고 있었다.** 쓰기를 끈 레디스 판에서 초당 1000건을 부르니 요청의
47% 가 `Can't assign requested address` 로 실패했다. 후보 30명의 상태를 파이프라인으로 읽는데, 파이프라인은 전용 연결을
따로 잡고, dispatch-engine 엔 풀이 없어서 그걸 매번 새로 열고 닫았다. 검색 100번에 연결이 102개 생겼고, 닫힌 연결이
TIME_WAIT 로 포트를 쥐고 있다가 로컬 포트가 바닥났다. 풀을 켜니 검색 100번에 3개, 실패 0 이 됐다. main 에 고쳐 넣었다(PR #23).

**MySQL 공간 컬럼 DDL 이 Debezium 을 죽였다.** 실험 테이블을 `pos POINT NOT NULL SRID 4326` 으로 만든 순간부터
주문 이벤트가 한 건도 안 나갔다. Debezium 은 binlog 에 지나가는 DDL 을 전부 해석해서 스키마 이력을 들고 있는데,
`SRID` 속성을 못 읽고 `DDL statement couldn't be parsed` 로 태스크가 FAILED 가 됐다. 커넥터 상태는 RUNNING 이었다
(1절에서 겪은 것과 같은 모양이다). 우리가 캡처하는 건 `outbox` 테이블 하나뿐인데도 다른 테이블의 DDL 때문에 멈췄다.
개발 환경은 커넥터에 `schema.history.internal.skip.unparseable.ddl=true` 를 잠깐 넣어 그 DDL 을 건너뛰게 한 뒤
원래 설정으로 되돌렸다. 계속 켜두면 나중에 진짜 읽어야 할 DDL 도 조용히 넘어간다. 공간 인덱스를 MySQL 로 가져오면
**CDC 까지 같이 챙겨야 한다**는 뜻이다.

### 그래서 어느 쪽을 쓰나

**레디스 GEO 를 그대로 둔다.** 이유는 세 가지다.

1. **좌표 쓰기를 못 따라간다.** 라이더 1만 명(초당 3333건)에서 MySQL 이 CPU 한 코어를 꽉 채우고, geo-indexer 는
   랙이 쌓여 좌표를 버리기 시작했다. 후보 검색보다 이게 먼저 터진다.
2. **읽기가 쓰기에 끌려간다.** 쓰기가 없으면 초당 170건이던 검색이 쓰기가 붙으면 48건이 된다. 점심 피크엔 좌표도 주문도
   같이 늘어나니, 제일 필요할 때 제일 느려진다.
3. **30명에서 멈추지 못한다.** 네모 안의 900명을 다 계산해야 30명을 고를 수 있다. 라이더가 몰리는 곳일수록 느려진다.

MySQL 쪽이 나은 것도 있긴 하다. 좌표와 주문을 한 트랜잭션에서 조인할 수 있고, 떨어져도 디스크에 남는다. 이 프로젝트에선
좌표가 3초면 새로 오고 레디스가 날아가도 다음 좌표로 다시 채워지니까, 그 장점이 필요한 자리가 없다.
