# 10초 뒤에 저절로 울리는 알람 — 래빗엠큐 타이머

라이더에게 배차를 제안하고 나서 **10초 안에 안 받으면 다음 사람에게 넘긴다.**
이 한 줄을 어떻게 만들었는지 적어둔다. 숫자는 전부 직접 재봤다.

---

## 어떻게 도는가

먼저 전체를 한 번 보자.

1. 가게 근처에서 지금 한가한 라이더를 찾아 점수순으로 열 명을 줄 세운다
2. 1순위에게 제안을 던진다. 이때 `dispatch.x` 에 **한 번만** 발행한다
3. 브로커가 그 메시지를 큐 두 개에 복사해 넣는다
   - `dispatch.offer.notify` — 워커가 바로 꺼내서 라이더 폰에 알림을 쏜다
   - `dispatch.offer.timer` — **아무도 안 꺼낸다.** 여기서 10초가 흐른다
4. 라이더가 10초 안에 안 받으면, 타이머 큐에 있던 메시지가 `dispatch.offer.expired` 로 옮겨간다
5. offer-relay 가 그걸 꺼내서 2순위에게 다시 제안한다. 그러면 3번으로 돌아간다
6. 누가 받거나, 다섯 번을 채우거나, 후보가 떨어지면 끝난다

**우리 코드에는 반복문이 없다.** 5번에서 다시 발행하면 타이머가 새로 걸리니까,
브로커가 그 반복을 대신 돌려준다.

## 카프카로는 왜 못 하나

두 가지가 걸린다.

**"10초 뒤에 읽어라" 를 적어둘 데가 없다.** 카프카는 메시지를 넣으면 바로 읽을 수 있는
상태가 되고, 언제 읽을지는 컨슈머가 정한다. 시간을 지정하는 자리가 아예 없다.

**"이 사람에게만" 을 적어둘 데도 없다.** 카프카는 파티션을 나눠서 읽는 구조라
"3번 라이더만 이 메시지를 봐라" 를 표현할 방법이 없다.

직접 만들려면 이렇게 된다. 제안을 보낼 때 DB 에 "10초 뒤에 만료" 라고 한 줄 넣고,
1초마다 도는 스케줄러가 시각이 지난 줄을 훑는다. 동작은 하는데, 이게 곧 래빗엠큐가
이미 해주는 걸 손으로 다시 만드는 것이다. 게다가 서버를 여러 대 띄우면 같은 줄을 둘이
집어가지 않게 또 막아야 한다. 아웃박스 폴러에서 겪은 문제가 그대로 반복된다
([`tech-choice.md`](tech-choice.md) 1번).

## 왜 컨슈머 없는 큐에 넣나

여기가 제일 안 와닿는 부분이라 따로 적는다. 이유가 세 가지다.

**첫째, 만료된 걸 아무도 모르면 주문이 그대로 멈춰 선다.**

```
10:00:00  1순위에게 제안을 던졌다. 현황판에 "제안 보냄" 이라고 적었다
10:00:10  라이더가 아무 반응이 없다
10:05:00  주문은 아직도 "제안 보냄" 그대로다
          손님은 5분째 배달원을 찾는 중이라는 화면만 보고 있다
```

2순위에게 넘어가려면 누군가 "1순위가 안 받았다" 를 알아채야 한다. 그런데 메시지가
조용히 사라지면 알아챌 사람이 아무도 없다.

**둘째, 그 10초를 셀 사람이 우리 쪽에 없다.**

제안을 던지는 순간 dispatch-engine 이 하던 일은 거기서 끝난다. 카프카 메시지를 ack 하고
스레드를 반납하고 다음 주문을 받으러 간다. 앉아서 10초를 세는 스레드가 없다.

스레드를 하나 띄워서 재우면 되지 않나 싶지만, 배포하느라 서버를 재시작하면 자던 스레드가
통째로 날아간다. 그 주문은 영영 방치된다. 게다가 초당 200건이 들어오면 자고 있는 스레드가
2000개다. 그래서 세는 일은 브로커에게 맡긴다. 브로커는 원래 안 죽고 떠 있는 게 일이다.

**셋째, 큐 하나가 이 둘을 같이 못 한다.**

TTL 이 흐르려면 그 큐에 컨슈머가 없어야 한다. 컨슈머가 있으면 들어오자마자 꺼내가서
10초가 흐를 틈이 없다. 반대로 만료를 알리려면 컨슈머가 있어야 한다. 요구가 정반대다.

그래서 큐를 두 개로 나누고, 시간이 다 되면 메시지를 옮긴다. 병원으로 치면 대기실과 진료실이다.
대기실에는 부르는 사람이 없어야 기다린다는 게 성립하고, 진료실에는 의사가 앉아 있어야 한다.
대기실에 의사를 앉혀두면 들어오는 족족 진료해버려서 기다림이라는 게 없어진다.

## 큐 선언

```java
Queue timer = QueueBuilder.durable("dispatch.offer.timer")
        .ttl(10_000)                          // 10초가 지나면 이 큐에서 빠진다
        .deadLetterExchange("dispatch.dlx")   // 빠질 때 그냥 버리지 말고 여기로 보낸다
        .deadLetterRoutingKey("offer.expired")// 보낼 때 이름표를 새로 붙인다
        .build();
```

`ttl`(time to live, 메시지 유통기한)은 우유에 찍힌 날짜와 같다. 지나면 큐에서 빠진다.
`deadLetterExchange`(만료된 메시지를 받아주는 익스체인지)는 **빠진 걸 어디로 보낼지**
정하는 값이다. 이걸 안 주면 그냥 사라진다. 우체국에서 수취인 불명 편지를 버리지 않고
반송 창구로 넘기는 것과 같다.

## 실제로 재봤다

관리 API 로 한 번 발행하고, 만료 큐를 50ms 마다 읽으면서 언제 오는지 쟀다.

```
발행 → 만료 큐 도착까지 : 10031ms   (걸어둔 시간은 10000ms)
```

31ms 늦었다. **래빗엠큐는 "이 시각에 정확히" 가 아니라 "적어도 이만큼은 지난 뒤" 로 동작한다.**
10초가 10.03초가 되어도 우리는 상관없지만, 밀리초를 다투는 곳이라면 이 방식을 쓰면 안 된다.

넘어온 메시지를 열어보니 이랬다.

```
지금 이름표      : offer.expired
원래 이름표      : offer.created
어느 큐에 있었나 : dispatch.offer.timer
왜 나왔나        : expired
본문             : {"offerId":1,"orderId":2,"riderId":3,"attempt":1}
```

**본문은 하나도 안 바뀌고 이름표만 갈렸다.** 이게 중요하다. offer-relay 는 메시지에 실려온
`offerId` 를 현황판에 적힌 값과 맞춰보고 낡은 메시지를 걸러내는데, 원본이 그대로 오니까
그 비교가 가능하다.

낡은 메시지가 왜 생기냐면 이렇다. 라이더가 3초에 거절해서 이미 2순위로 넘어갔는데,
10초가 되면 1순위용 타이머가 뒤늦게 도착한다. 그걸 그대로 처리하면 **아직 살아 있는 2순위
제안을 끊고 3순위로 넘어가버린다.** 재제안할 때마다 `offerId` 를 새로 발급하는 이유가 이거다.

## TTL 을 큐에 걸까, 메시지마다 걸까

우리는 큐 단위로 걸었다(`x-message-ttl`). 제안이 전부 10초로 같아서 메시지마다 다르게 줄
이유가 없다.

메시지 단위로 거는 방법(`expiration` 속성)도 있는데 함정이 있다.
**래빗엠큐는 큐 맨 앞에 있는 메시지만 시간을 확인한다.** 뒤쪽은 안 본다.

8초짜리와 1초짜리를 순서만 바꿔서 넣고 3초 뒤에 큐를 세봤다.

| 넣은 순서 | 3초 뒤 남은 건수 |
|---|---|
| 8초짜리 먼저, 1초짜리 나중 | **2건** — 1초짜리가 시간이 한참 지났는데 안 빠졌다 |
| 1초짜리 먼저, 8초짜리 나중 | 1건 — 맨 앞이라 제때 빠졌다 |

첫 줄이 함정이다. 앞에 오래 사는 게 서 있으면 뒤에 있는 짧은 건 자기 시간이 지나도 못 나온다.
은행 창구에서 앞사람이 안 비키면 볼일 다 본 뒷사람도 못 나가는 것과 같다.

우리는 큐 전체에 같은 시간을 걸었으니 들어온 순서가 곧 빠지는 순서다. 이 문제가 없다.
나중에 "급한 주문은 5초, 보통은 10초" 같은 걸 하고 싶어지면 이 함정을 먼저 떠올려야 한다.
그때는 큐를 시간대별로 나누는 게 맞다.

## 아직 안 해본 것

- **몇 번까지 돌지 막는 걸 안 만들었다.** 지금은 offer-relay 가 다섯 번을 세서 끊는데,
  메시지에 붙어 오는 `x-death` 헤더에도 몇 번 만료됐는지가 들어 있다. 그걸로 막는 게 더 정확하다.
- **브로커를 재시작하면 세던 시간이 어떻게 되는지 안 재봤다.** 큐는 durable 로 선언했지만
  남은 시간이 이어지는지 확인이 필요하다. 5단계 카오스 테스트에서 본다.
- **타이머 큐가 얼마나 쌓여도 견디는지 모른다.** 초당 200 주문이면 항상 2000건쯤이 이 큐에
  떠 있게 된다. 메모리를 얼마나 먹는지 4단계에서 잰다.
