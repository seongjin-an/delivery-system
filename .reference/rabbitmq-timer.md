# 래빗엠큐 타이머 — 10초 뒤에 저절로 울리는 알람

배차 제안을 보내고 나서 **10초 안에 안 받으면 다음 사람에게 넘긴다**. 이 한 줄을 어떻게
만드느냐가 이 프로젝트에서 래빗엠큐를 쓰는 이유 전부다.

이 문서는 그 장치가 실제로 어떻게 도는지 정리한 것이다. 숫자는 전부 직접 재본 값이다.

---

## 1. 풀어야 하는 문제

라이더 한 명을 골라 제안을 보냈다. 그다음에 필요한 게 세 가지다.

1. **딱 그 사람에게만** 알림이 가야 한다
2. **10초를 세다가** 응답이 없으면 알아야 한다
3. 그러면 **다음 후보에게 넘어가야** 한다

2번이 어렵다. "지금 처리해라" 가 아니라 "10초 뒤에 처리해라" 이기 때문이다.

## 2. 카프카로는 왜 안 되나

카프카에는 **"언제 읽을지" 를 정하는 장치가 없다.** 메시지를 넣으면 컨슈머가 읽을 수 있는
상태가 되고, 언제 읽을지는 컨슈머 마음이다. "10초 뒤에 읽어라" 를 메시지에 붙일 방법이 없다.

직접 만든다면 이렇게 된다.

```
제안 보낼 때  →  DB 에 "이 제안은 10초 뒤에 만료" 라고 한 줄 넣기
               →  1초마다 도는 스케줄러가 "만료 시각 지난 줄" 을 훑기
               →  찾으면 다음 후보로 넘기기
```

동작은 한다. 그런데 이건 **래빗엠큐가 이미 해주는 걸 손으로 다시 만드는 것**이다. 게다가
스케줄러가 1초마다 돌면 지연이 최대 1초씩 더 붙고, 인스턴스를 여러 대 띄우면 같은 줄을 둘이
집어가지 않게 또 막아야 한다. (아웃박스 폴러에서 겪은 그 문제가 그대로 반복된다.
`tech-choice.md` 1번 참고)

1번도 걸린다. 카프카는 파티션 단위로 나눠 읽는 구조라 "이 메시지는 3번 라이더만 봐라" 를
표현할 수가 없다.

## 3. 래빗엠큐가 주는 장치 두 개

### 3.1 메시지 유통기한 (`x-message-ttl`)

큐에 유통기한을 걸어두면, 그 큐에 들어온 메시지는 그 시간이 지나는 순간 **자동으로 큐에서
빠진다.** 우유에 찍힌 유통기한과 같다. 아무도 안 마시면 날짜가 지나고, 지나면 버려진다.

### 3.2 버려지는 메시지를 받아주는 곳 (`x-dead-letter-exchange`)

유통기한이 지난 메시지는 기본적으로 **그냥 사라진다.** 그런데 우리한테는 사라지면 안 된다.
그래서 **"버릴 때 그냥 버리지 말고 저기로 보내라"** 를 같이 지정한다. 이게 데드레터
익스체인지다.

우체국에서 "수취인 불명" 편지를 그냥 버리지 않고 반송 창구로 넘기는 것과 같다. 편지 자체는
그대로인데 도장이 하나 더 찍혀서 다른 창구로 간다.

이 둘을 합치면 **"10초 뒤에 저절로 울려서 다른 곳으로 넘어가는 알람"** 이 된다.

왜 사라지면 안 되는지, 왜 하필 다른 큐로 보내야 하는지는 6장에서 따로 다룬다.

## 4. 우리가 선언한 큐

```java
Queue timer = QueueBuilder.durable("dispatch.offer.timer")
        .ttl(10_000)                                  // 10초 지나면 이 큐에서 빠진다
        .deadLetterExchange("dispatch.dlx")           // 빠질 때 여기로 보낸다
        .deadLetterRoutingKey("offer.expired")        // 보낼 때 이 이름표를 새로 붙인다
        .build();
```

실제로 브로커에 어떻게 들어갔는지 확인한 값이다.

```
x-message-ttl             = 10000
x-dead-letter-exchange    = dispatch.dlx
x-dead-letter-routing-key = offer.expired
```

## 5. 실제로 재본 결과

관리 API 로 `dispatch.x` 에 한 번 발행하고, 만료 큐를 50ms 마다 읽으면서 언제 도착하는지 쟀다.

```
발행 → 만료 큐 도착까지: 10031ms   (걸어둔 시간은 10000ms)
```

31ms 늦었다. **래빗엠큐의 유통기한은 "이 시각에 정확히" 가 아니라 "적어도 이만큼은 지난 뒤"** 다.
우리는 10초가 10.03초가 되어도 아무 상관이 없지만, 밀리초 단위 정확도가 필요한 곳이라면
이 방식은 맞지 않는다.

### 넘어온 메시지가 어떻게 바뀌었나

```
지금 라우팅 키  : offer.expired
원래 라우팅 키  : ['offer.created']
어느 큐에 있었나 : dispatch.offer.timer
왜 나왔나       : expired
본문            : {"offerId": 1, "orderId": 2, "riderId": 3, "attempt": 1}
```

**본문은 하나도 안 바뀌고 이름표만 갈렸다.** `offer.created` 로 들어온 메시지가 `offer.expired`
가 되어 나온다. 그리고 `x-death` 라는 헤더가 새로 붙어서 "원래 어느 큐에 있었고 왜 나왔는지" 가
기록된다. 이 헤더는 나중에 offer-relay 가 무한 재제안을 막을 때 쓸 수 있다.

## 6. 왜 굳이 다른 큐로 보내야 하나

여기가 이 구조에서 제일 중요한 부분인데, 앞에서 "이렇게 간다" 만 적고 이유를 안 적었다.
이유가 세 겹이다.

### 6.1 사라지게 두면 주문이 방치된다

유통기한이 지난 메시지를 그냥 사라지게 두면 어떻게 되는지 따라가 보자.

```
10:00:00  1순위 라이더에게 제안을 보냈다
          dispatch:offer 에 state=OFFERED 라고 적었다
10:00:10  라이더가 아무 반응이 없다. 타이머 메시지가 만료돼 사라졌다
          ...
10:05:00  주문은 아직도 state=OFFERED 다
          손님은 5분째 "배달원을 찾는 중" 화면을 보고 있다
```

**아무 일도 안 일어난다.** 라이더가 안 받았다는 사실을 아는 사람이 없기 때문이다.
2순위에게 넘어가려면 누군가 "1순위가 안 받았다" 를 알아야 하는데, 메시지가 조용히 사라지면
그걸 아는 주체가 세상에 없다.

그러니까 만료는 **버리는 동작이 아니라 알리는 동작**이어야 한다.
"이 제안은 무응답으로 끝났다" 는 사실을 누군가에게 전달해야 한다.

### 6.2 그 알림을 우리 코드가 스스로 만들 수 없다

그럼 우리 코드가 알아서 세면 되지 않나 싶은데, 셀 주체가 없다.

제안을 보내는 순간 dispatch-engine 이 하던 일은 **거기서 끝난다.** 카프카 메시지를 ack 하고,
스레드는 반환되고, 다음 주문을 받으러 간다. 10초를 세면서 앉아 있는 스레드가 없다.

스레드를 하나 띄워서 10초 자게 하면 되지 않나 싶지만 그것도 안 된다.

- 그 서버가 배포로 재시작되면 자고 있던 스레드가 통째로 날아간다. 그 주문은 영영 방치된다
- 주문이 초당 200건이면 자고 있는 스레드가 2000개다
- 인스턴스를 늘리면 어느 서버가 어느 제안을 세고 있는지 아무도 모른다

그래서 **세는 일을 브로커에게 맡긴다.** 브로커는 원래 안 죽고 계속 떠 있는 게 일이고,
메시지를 디스크에 들고 있으니 재시작해도 남는다.

### 6.3 한 큐가 두 가지를 동시에 할 수 없다

여기가 핵심이다. 필요한 게 두 가지인데 서로 정반대다.

| | 필요한 조건 |
|---|---|
| 10초를 세려면 | 그 큐에 **컨슈머가 없어야** 한다. 있으면 바로 꺼내가서 시간이 안 흐른다 |
| 만료를 알리려면 | 그 큐에 **컨슈머가 있어야** 한다. 없으면 아무도 못 듣는다 |

한 큐가 이 둘을 같이 만족할 수 없다. 컨슈머가 있으면 시간이 안 흐르고, 없으면 알림이 안 간다.

그래서 큐를 두 개로 나눈다.

```
dispatch.offer.timer     컨슈머 없음    시간이 흐르게 두는 곳
        │ 10초 지남
        ▼
dispatch.offer.expired   컨슈머 있음    무응답을 알려주는 곳
```

**메시지가 이사를 가는 이유가 이것이다.** 시간을 세는 방에는 아무도 없어야 하고, 소식을 듣는
방에는 사람이 있어야 하니까, 시간이 다 되면 메시지를 사람이 있는 방으로 옮기는 것이다.

병원 대기실에 비유하면 이렇다. 대기실(타이머 큐)에는 부르는 사람이 없다. 그냥 앉아서 시간이
가기를 기다리는 곳이다. 시간이 되면 진료실(만료 큐)로 옮겨지고, 거기엔 의사가 앉아 있다.
대기실에 의사를 앉혀두면 들어오자마자 진료를 시작해서 대기라는 게 없어진다.

### 6.4 받은 쪽은 뭘 하나

`dispatch.offer.expired` 를 offer-relay 가 꺼내서 순서대로 확인한다 (RE-02).

1. 메시지의 `offerId` 가 현황판의 현재 `offerId` 와 **다르면 버린다.**
   라이더가 이미 거절해서 3초에 2순위로 넘어갔는데, 10초가 되면 1순위용 타이머가 뒤늦게
   도착한다. 그걸 그대로 처리하면 **아직 유효한 2순위 제안을 끊고 3순위로 넘어가버린다.**
   메시지 안에 `offerId` 가 그대로 실려 오기 때문에 이 비교가 가능하다
2. 이미 수락됐으면(`ACCEPTED`) 버린다. 라이더가 9초에 수락했을 수 있다
3. 주문이 취소됐으면 키들을 정리하고 끝낸다
4. 시도 횟수가 5번을 넘었으면 포기하고 `dispatch.failed` 를 발행한다
5. **직전 라이더의 찜을 풀고 상태를 `IDLE` 로 되돌린다.** 이걸 빼먹으면 그 라이더는
   12초 동안 다른 주문의 후보가 못 된다
6. 다음 후보를 꺼낸다
7. 새 `offerId` 를 발급하고 시도 횟수를 1 올린다
8. `offer.created` 를 다시 발행한다 → 다시 두 큐로 복제되고, 타이머가 새로 10초를 센다

**8번에서 고리가 닫힌다.** 재발행하면 타이머가 또 걸리니까, 수락되거나 후보가 떨어질 때까지
10초 간격으로 계속 돈다. 우리 코드 어디에도 반복문이 없는데 브로커가 그 반복을 만들어준다.

1번이 이 메시지가 **사라지지 않고 원본 그대로 흘러가야 하는 이유**이기도 하다. 만료 통지를
새로 만들어 보내면 어느 제안이 만료된 건지 다시 붙여야 하는데, 원본이 그대로 오니까 그럴 필요가 없다.

## 7. 이름표가 바뀌는 게 왜 중요한가

이름표(라우팅 키)는 **이 메시지를 어느 큐에 넣을지 정하는 값**이다. 우편번호와 같다.
편지를 우체국에 낼 때 우편번호를 적어주면 우체국이 그 번호에 맞는 동네로 보낸다.

```
dispatch.x  ──(offer.created)──┬─▶ dispatch.offer.notify   알림 워커가 바로 꺼내간다
                               └─▶ dispatch.offer.timer    아무도 안 꺼낸다. 10초를 센다
                                       │ 10초 지남
                                       ▼
                       dispatch.dlx ──(offer.expired)──▶ dispatch.offer.expired
                                                              │
                                                       offer-relay 가 꺼내서
                                                       다음 후보에게 재제안
```

같은 메시지가 이름표만 갈아 끼우고 전혀 다른 목적지로 간다. 메시지를 새로 만들어 보내는 게
아니라 원본이 그대로 흘러가는 것이라, 안에 든 `offerId` 와 `orderId` 가 유지된다.
offer-relay 는 그 값을 보고 "이게 아직 유효한 제안인가" 를 판단한다.

## 8. 타이머 큐에는 컨슈머를 붙이면 안 된다

이게 처음 만들 때 제일 헷갈리는 부분이다.

큐를 만들었으니 뭔가 읽는 쪽을 붙여야 할 것 같은데, **붙이는 순간 망가진다.** 컨슈머가 있으면
메시지가 큐에 들어오자마자 꺼내가고, 그러면 10초를 셀 시간이 없다. 유통기한이 지나기 전에
누가 먹어버리는 것과 같다.

알람시계를 맞춰놓고 울리기 전에 꺼버리는 셈이다. 알람이 안 울리니 재제안이 한 번도 안 돈다.
그런데 **에러는 아무 데서도 안 난다.** 큐도 있고 메시지도 잘 들어가고 컨슈머도 잘 받는다.
그냥 만료가 영영 안 일어날 뿐이다. 그래서 찾기가 고약하다.

정리하면 이 큐는 **일부러 아무도 안 읽는 큐**다. 메시지를 담아두는 게 목적이 아니라 시간이
흐르게 두는 게 목적이다.

## 9. 발행 한 번이 메시지 두 개가 되는 구조

`dispatch.x` 는 토픽 익스체인지고, 이름표 `offer.created` 에 큐 **두 개**가 묶여 있다.
그래서 한 번 발행하면 브로커가 알아서 두 개로 복제해 넣는다.

실제로 확인한 결과다.

```
브로커가 어느 큐에든 넣었나(routed): True
알림 큐에 도착한 건수: 1        ← 발행은 한 번인데 여기 들어왔다
10초 뒤 만료 큐에 도착: 1       ← 타이머 큐에 있던 것이 넘어왔다
```

### 왜 코드에서 두 번 보내면 안 되나

알림 큐에 한 번, 타이머 큐에 한 번 따로 보내도 될 것 같다. 그런데 그러면 **한쪽만 성공하는
경우가 생기고, 그게 어느 쪽이든 사고다.**

| 어느 쪽이 실패했나 | 무슨 일이 나나 |
|---|---|
| 타이머만 실패 | 라이더가 안 받아도 아무도 모른다. 그 주문은 방치된다 |
| 알림만 실패 | 라이더는 제안이 온 줄도 모르는데 10초 뒤에 거절한 걸로 처리된다. 그 사람 거절률만 올라간다 |

발행을 한 번으로 만들면 **갈림길 자체가 없어진다.** 성공이면 둘 다 있고 실패면 둘 다 없다.
주문 행과 이벤트 행을 한 트랜잭션에 넣는 아웃박스 패턴과 똑같은 생각이다.

## 10. 유통기한을 큐에 걸까, 메시지마다 걸까

두 가지 방법이 있다.

| | 어디에 거나 | 어떻게 |
|---|---|---|
| 큐에 걸기 | 큐 선언할 때 | `x-message-ttl: 10000` |
| 메시지마다 걸기 | 보낼 때마다 | 메시지 속성 `expiration: "10000"` |

우리는 큐에 걸었다. 제안 유효시간이 전부 10초로 같아서 메시지마다 다르게 줄 이유가 없다.

### 그런데 메시지마다 다르게 주면 함정이 있다

**래빗엠큐는 큐 맨 앞에 있는 메시지만 유통기한을 확인한다.** 뒤쪽은 안 본다.

직접 재봤다. 유통기한 8초짜리와 1초짜리를 순서를 바꿔가며 넣고 3초 뒤에 큐를 봤다.

| 넣은 순서 | 3초 뒤 큐에 남은 건수 | 무슨 뜻인가 |
|---|---|---|
| 8초짜리 먼저, 1초짜리 나중 | **2건** | 1초짜리가 만료 시각을 한참 넘겼는데 아직 큐에 있다 |
| 1초짜리 먼저, 8초짜리 나중 | **1건** | 맨 앞이라 제때 빠졌다 |

첫 줄이 함정이다. 앞에 오래 사는 메시지가 서 있으면 **뒤에 있는 짧은 메시지는 자기 시간이
지났는데도 안 빠진다.** 은행 창구에서 앞사람이 안 비키면 뒤에 볼일 다 본 사람도 못 나가는 것과
같다. (읽어갈 때 만료된 건 건너뛰기 때문에 잘못된 메시지가 처리되지는 않지만, "제때 넘어간다"
는 보장이 깨진다.)

우리는 큐 전체에 같은 시간을 걸었으니 **들어온 순서가 곧 만료되는 순서**라 이 문제가 없다.
나중에 "VIP 주문은 5초, 일반은 10초" 같은 걸 하고 싶어지면 이 함정을 먼저 떠올려야 한다.
그때는 큐를 시간대별로 나누는 쪽이 맞다.

## 11. 한 장 정리

| 궁금한 것 | 답 |
|---|---|
| 10초를 누가 세나 | 브로커가 센다. 우리 코드에 타이머가 없다 |
| 정확한가 | 10000ms 걸고 10031ms 에 왔다. "최소 이만큼" 이지 정확한 시각이 아니다 |
| 만료되면 메시지가 사라지나 | 아니다. 데드레터로 옮겨간다. 본문은 그대로고 이름표만 바뀐다 |
| 왜 사라지면 안 되나 | 라이더가 안 받았다는 걸 아무도 모르게 되고, 그 주문은 영영 방치된다 |
| 왜 다른 큐로 옮기나 | 시간을 세려면 컨슈머가 없어야 하고 알리려면 있어야 하는데, 한 큐가 둘 다 못 한다 |
| 타이머 큐를 누가 읽나 | 아무도 안 읽는다. 읽으면 망가진다 |
| 발행은 몇 번 하나 | 한 번. 브로커가 두 큐로 복제한다 |
| 유통기한은 어디에 거나 | 큐에 건다. 메시지마다 다르게 주면 앞 메시지가 뒤를 막는다 |

## 12. 아직 안 해본 것

- **만료가 몇 번까지 도는지 막는 장치.** 지금은 후보가 떨어질 때까지 계속 돈다.
  `x-death` 헤더의 `count` 를 보면 몇 번 만료됐는지 알 수 있으니 그걸로 막을 수 있다. RE-02 몫이다.
- **브로커를 재시작했을 때 진행 중이던 타이머가 어떻게 되는지.** 큐는 durable 로 선언했지만
  메시지 자체가 영속으로 저장되는지, 남은 시간이 이어지는지 안 재봤다. 5단계 카오스 테스트에서 확인한다.
- **타이머 큐가 얼마나 쌓여도 괜찮은지.** 초당 200 주문이면 항상 2000건 정도가 이 큐에 떠 있게 된다.
  메모리를 얼마나 쓰는지 4단계에서 재본다.
