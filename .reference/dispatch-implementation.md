# 배차 엔진을 만들면서 (DE-01 ~ DE-03)

[`dispatch-internals.md`](dispatch-internals.md) 가 "이렇게 만들 것이다" 라면, 이 문서는
"만들어보니 이랬다" 를 적은 것이다. 설계와 달라진 부분과 실제로 확인한 값이 들어 있다.

## 1. 주문 하나가 제안 하나가 되기까지

레디스와 아홉 번 이야기한다.

```
order.created 도착
  │
  ├─ ① SET lock:dispatch:{주문번호} NX PX 15000     이 주문은 내가 처리한다
  ├─ ② HMGET dispatch:offer:{주문번호}              전에 처리한 적 있나?
  ├─ ③ GEOSEARCH riders:online ... ASC COUNT 30     가게 근처 30명
  ├─ ④ 파이프라인으로 rider:state 30개               그중 누가 한가한가
  ├─ ⑤ DEL + RPUSH dispatch:candidates + EXPIRE     점수순 10명 줄 세우기
  ├─ ⑥ LPOP                                        1순위 꺼내기
  ├─ ⑦ SET lock:rider:{라이더번호} NX PX 12000       이 사람 찜하기
  ├─ ⑧ HSET dispatch:offer + EXPIRE                 현황판에 적기
  │      └─ 래빗엠큐로 제안 발행 + 발행 확인
  └─ ⑨ Lua 로 ① 풀기
```

①~② 가 DE-01, ③~⑤ 가 DE-02, ⑥~⑧ 이 DE-03 이다.

## 2. 락이 두 개인데 지키는 게 다르다

기능 정의서에는 "리스(lease)" 라고 적혀 있는데, 그냥 **레디스 락**이다.
15초가 지나면 저절로 풀려서 "빌려 쓴다" 는 뜻으로 그렇게 부른 것뿐이다.
이 문서에서는 헷갈리지 않게 **배차 락**이라고 쓴다.

| | 무엇을 지키나 | 값에 뭐가 들어가나 | 얼마나 살아 있나 |
|---|---|---|---|
| `lock:dispatch:{주문번호}` | 주문 | 인스턴스 이름 | 15초 |
| `lock:rider:{라이더번호}` | 라이더 | **주문 번호** | 12초 |

**값이 다른 게 핵심이다.** 배차 락은 주인이 프로세스라 나만 풀 수 있어야 한다. 라이더 찜은
주인이 주문이라, 나중에 offer-relay 가 재제안할 때 그 락을 풀 수 있다. 자기가 처리하는
주문의 찜이니까. 대신 풀 때 값이 자기 주문인지 확인해야 한다. 그 사이 다른 주문이 채갔을 수 있다.

### 배차 락이 막는 것

카프카는 같은 메시지를 두 번 보낼 수 있다. 컨슈머가 일을 다 끝내고 오프셋을 커밋하기 직전에
죽으면, 다른 인스턴스가 그 메시지를 다시 받는다. 둘 다 배차하면 주문 하나에 라이더가 두 명 붙는다.

### 라이더 찜이 막는 것

강남에 한가한 라이더가 한 명인데 주문이 두 건 들어온 상황이다. 주문 두 개는 파티션이 달라서
서버 두 대가 각각 처리하고, 둘 다 그 라이더를 1순위로 뽑는다. 찜이 없으면 라이더 폰에 제안이
두 개 뜨고, 둘 다 수락하면 배달 두 개를 동시에 맡는다.

### 락 푸는 건 반드시 Lua 로

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

값 확인 없이 `DEL` 하면 이런 사고가 난다. A 가 락을 잡고 일하다 느려져서 15초를 넘겼다.
락이 저절로 풀리고 B 가 새로 잡았다. 뒤늦게 끝난 A 가 마무리로 `DEL` 을 한다.
**B 의 락을 A 가 지웠다.** 그러면 C 가 또 들어와서 B 와 같이 같은 주문을 배차한다.

화장실 문에 이름표를 걸어두고, 나올 때 그게 자기 이름표인지 보고 떼는 것이다.
남의 이름표가 걸려 있으면 안 건드리고 그냥 나온다.

## 3. 락만으로는 부족하다

배차 락은 **"지금 이 순간 누가 하고 있나"** 만 알려준다. 15초 뒤에 사라지니까
**"전에 처리한 적 있나"** 는 못 알려준다.

카프카에서 같은 주문 메시지가 20초 뒤에 또 오면 락은 이미 없어서 그냥 통과한다.
이미 제안이 나간 주문에 또 제안이 나간다.

그래서 `dispatch:offer:{주문번호}` 라는 해시를 따로 둔다. 10분 남아 있어서 늦게 온 중복
메시지를 걸러낸다.

| | 답해주는 질문 | 기억하는 기간 |
|---|---|---|
| 배차 락 | 지금 누가 하고 있나 | 15초 |
| `dispatch:offer` | 전에 한 적 있나 | 10분 |

`dispatch:offer` 는 락이 아니라 **데이터**다. 수락과 만료 중 어느 쪽이 이겼는지 판정하는
단 하나의 기준이기도 하다. 라이더의 수락은 dispatch-engine 이 받고 10초 뒤 만료는
offer-relay 가 받는데, 서로 다른 프로세스라 각자 자기 메모리에 들고 있으면 서로 뭘 아는지 모른다.
그러면 라이더가 9초에 수락했는데 offer-relay 가 그걸 모르고 10초에 2순위에게 또 제안하고,
2순위도 수락하면 **라이더 두 명이 같은 가게에 나타난다.**

## 4. 좀비 주문 판정

`dispatch:offer` 를 읽고 이 표대로 판단한다.

| 읽은 값 | 어떻게 |
|---|---|
| 키가 없다 | 처음 보는 주문 → 진행 |
| `ACCEPTED` / `CANCELLED` | 끝난 주문 → 넘어감 |
| `EXPIRED` / `FAILED` / `REJECTED` | 끝났지만 다시 해도 됨 → 진행 |
| `OFFERED` 이고 30초 안쪽 | 아직 진행 중 → 넘어감 (offer-relay 가 이어받는다) |
| `OFFERED` 인데 30초 넘음 | **좀비** → 진행 |

마지막 줄이 이 표가 있는 이유다.

제안은 10초짜리다. 그런데 30초가 지나도 `OFFERED` 로 남아 있다면 **만료 알람이 애초에 안
걸린 것**이다. 정상이면 10초에 만료돼서 `EXPIRED` 로 바뀌어 있어야 한다. 래빗엠큐 발행이
반쯤 실패했다든가 해서 알람시계가 안 맞춰진 경우다.

여기서 "키가 있네, 넘어가자" 하고 지나가면 그 주문은 **아무도 안 건드린 채로 영영 남는다.**
손님만 하염없이 기다린다. 그래서 시간까지 봐야 한다.

30초라는 값은 offer-relay 의 큐가 얼마나 밀리는지 보고 조정할 값이다.

## 5. 후보를 찾는 건 두 단계다

레디스 GEO 는 별도의 자료구조가 아니라 그냥 정렬된 집합(sorted set)이다.
그래서 **좌표밖에 모른다.** 그 라이더가 지금 배달 중인지, 방금 제안을 거절했는지를 GEO 는
전혀 모른다. 그건 `rider:state` 해시에 따로 있다.

```
GEOSEARCH 로 거리순 30명        ← 거리만 아는 단계
     ↓
30명의 rider:state 를 한꺼번에   ← 상태를 붙이는 단계
     ↓
IDLE 인 사람만 남기고 점수순 10명
```

실제로 돌려봤을 때 라이더 4명 중 배달 중이던 한 명도 GEOSEARCH 에는 딸려 나왔다.
상태를 붙이는 단계에서 걸러졌다. **이 단계가 없으면 배달 중인 사람에게 제안이 간다.**

### 30명 뽑아서 10명만 쓰는 이유

걸러질 걸 감안한 여유분이다. 점심시간에는 절반 이상이 배달 중이라 30명 중 12명만 남기도 한다.
10명만 뽑으면 거르고 나서 남는 게 없다.

### `COUNT` 와 `ASC` 는 반드시 같이 준다

```
GEOSEARCH riders:online FROMLONLAT {경도} {위도} BYRADIUS 3000 m ASC COUNT 30 WITHDIST
```

둘 다 줘야 레디스가 가까운 순으로 세다가 30명에서 멈춘다.
`ASC` 없이 `COUNT` 만 주면 "아무 30명" 이고, `COUNT` 없이 `ASC` 만 주면 반경 안 500명을
전부 계산하고 정렬해서 실어 보낸다.

지하철에서 "앞에서부터 서른 명만 세주세요" 와 "다 세고 나서 앞의 서른 명" 의 차이다.

### 상태 조회는 파이프라인으로 묶는다

30명 상태를 for 루프로 조회하고 싶어진다. 로컬에서는 레디스가 같은 컴퓨터에 있어서 왕복 한 번이
0.1ms 고 30번 해도 3ms 다. **아무 문제 없어 보인다.**

그런데 실제 환경에서 레디스가 다른 서버에 있으면 왕복 한 번이 1ms 다. 30번이면 30ms.
**배차 하나에 30ms 를 상태 조회에만 쓰는 셈이다.** 목표가 "주문에서 첫 제안까지 1초" 인데
여기서만 30ms 를 흘린다.

파이프라인은 편지 서른 통을 한 봉투에 담아 보내는 것이다. 우체국을 서른 번 왕복하는 대신
한 번 간다. 명령들이 한 덩어리로 실행되는 건 아니라서 사이에 다른 클라이언트 명령이 끼어들 수
있는데, 여기서는 읽기만 하니 상관없다.

### 점수는 낮을수록 우선

```
점수 = 거리km − 대기보너스
대기보너스 = min(대기시간_분, 10) × 0.1
```

반경이 3km 니까 거리 항은 0에서 3 사이고 보너스는 최대 1.0 이다.
10분 넘게 기다린 라이더는 1km 정도 더 멀어도 가까운 라이더를 이긴다.

보너스가 없으면 가게 바로 앞에 있는 라이더가 콜을 독식하고, 조금 떨어진 사람은 하루 종일 논다.

## 6. 발행하고 나서 답을 기다린다

`convertAndSend` 는 기본적으로 **던지고 답을 안 기다린다.** 브로커가 받았는지 모른 채 다음
줄로 넘어간다.

우리 코드 순서가 이래서 문제가 된다.

```
1. HSET dispatch:offer  state=OFFERED     현황판에 "제안 보냄" 이라고 적고
2. HSET rider:state     status=OFFERED    라이더도 "제안 받음" 으로 바꾸고
3. 래빗엠큐로 발행
```

3번이 실패했는데 코드가 모르면, **아무한테도 안 간 제안이 현황판에는 `OFFERED` 로 남는다.**
라이더는 알림을 못 받았고 만료 알람도 없다. 그리고 30초 뒤에 다음 시도가 와서 좀비 판정에
걸린다. 30초를 그냥 날리는 것이다.

그래서 발행 확인을 켰다.

```yaml
spring.rabbitmq.publisher-confirm-type: correlated
```

```java
CorrelationData confirm = new CorrelationData(Long.toString(offerId));
rabbitTemplate.convertAndSend(exchange, routingKey, offer, confirm);

if (!confirmed(confirm, ...)) {
    offerBoard.clear(orderId);                   // 현황판 지우고
    // rider:state 를 IDLE 로 되돌리고
    return null;                                 // 다음 후보로 간다
}
```

`CorrelationData` 는 영수증 번호 같은 것이다. 발행할 때 같이 넘기면 브로커가 "받았다 / 못
받았다" 를 답할 때 그 번호를 붙여 보내준다. 그래서 어느 메시지가 실패했는지 가릴 수 있다.

설정값이 `simple` 도 있는데 그건 채널 단위로 기다리는 방식이라 메시지별로 구분이 안 된다.

**중요한 건 실패했을 때 되돌리는 부분이다.** 안 되돌리면 위에서 말한 유령 제안이 남는다.

## 7. 기능 정의서와 달라진 것 두 개

### 7.1 래빗엠큐 큐 선언을 `libs/common` 으로 옮겼다

문서에는 offer-relay(RE-01)가 선언한다고 돼 있다. 그런데 그러면 dispatch-engine 이
offer-relay 보다 먼저 뜰 때 큐가 없고, **큐가 없는 익스체인지에 발행하면 메시지가 에러도 없이
그냥 사라진다.** 조용히 없어지는 종류라 찾기가 아주 어렵다.

`libs/common` 에 두고 래빗엠큐를 쓰는 서비스가 다 같이 선언하게 했다. 스프링 AMQP 의 선언은
같은 걸 여러 번 해도 안전해서, 겹쳐도 문제가 없고 어느 서비스를 먼저 띄우든 큐가 준비돼 있다.

### 7.2 `rider:state` 에 `idleSince` 를 새로 정했다

DE-02 의 대기 보너스가 "대기시간" 을 쓰는데, 그 값이 어디서 오는지가 문서에 없었다.
그래서 "IDLE 이 된 시각" 을 담는 필드를 새로 만들었다.

**`status` 를 `IDLE` 로 바꾸는 쪽(GI-01, DE-05, OR-04)이 이 값도 같이 써야 한다.**
안 써도 에러가 안 나고 보너스만 0이 될 뿐이라 더 눈에 안 띈다. 그래서 상수 클래스 주석에
크게 적어뒀다.

## 8. 실제로 돌려본 결과

geo-indexer 가 아직 없어서 라이더 4명을 레디스에 직접 넣고 주문 하나를 만들었다.

| 확인한 것 | 결과 |
|---|---|
| 타이머 큐 / 알림 큐 | 각각 1건 (발행은 한 번, 브로커가 복제) |
| 10초 뒤 | 타이머 큐 0건, 만료 큐 1건 |
| 1순위 | 가장 가까운 라이더, 남은 후보는 점수순으로 정렬됨 |
| 배달 중이던 라이더 | 후보에서 아예 빠짐 |
| `order.status` | `DISPATCHING` 발행됨 |
| 배차가 끝난 뒤 배차 락 | 0개 (제대로 풀림) |

### 뜻밖에 본 것 — 과거 주문 221건이 한꺼번에 다시 배차됐다

dispatch-engine 을 처음 띄우자 `반경 3000m 안에 한가한 라이더가 없다` 로그가 221줄 찍혔다.

컨슈머 그룹이 처음 만들어지는데 `auto-offset-reset: earliest` 라서, 그동안 테스트로 쌓아둔
`order.created` 221건을 전부 다시 읽고 배차를 시도한 것이다. 라이더가 없던 시점 주문들이라
전부 실패로 끝났다.

설정대로 동작한 것이라 잘못된 건 아니다. 다만 **새 컨슈머 그룹을 붙이면 토픽에 쌓인 과거분이
통째로 재생된다**는 걸 눈으로 봤다. 6단계에서 정산을 오프셋 리셋으로 재계산할 때 똑같은 일이
일어나는데, 그때는 그게 목적이다.

## 9. 남은 것과 정해야 할 것

### 아직 안 만든 것

- **Lua 스크립트 3종 중 하나만 했다.** 락 풀기만 있고 제안 수락(DE-04)과 만료 처리(RE-02)가 남았다.
- `dispatch.offer.notify` 에 쌓인 메시지를 아무도 안 꺼내간다. notification-worker(NW-01) 몫이다.
- 만료 큐로 넘어간 메시지도 아무도 안 꺼내간다. offer-relay(RE-02) 몫이다.
- 라이더를 아직 손으로 넣어야 한다. geo-indexer(GI-01)가 생기면 실제 좌표로 들어온다.

### 정해야 할 것

**`attempt` 를 언제 올릴 것인가.** 지금 코드는 발행이 실패했을 때만 올린다. 후보가 이미 다른
주문에 찜당해서 건너뛰면 안 올린다. 그래서 3명을 건너뛰고 4번째에게 제안이 나가도 `attempt` 는
1로 기록된다.

기능 정의서는 `attempt` 를 "몇 번째 라이더에서 잡혔나" — 고객 지원에서 보라고 넣은 값이라고
설명한다. 그 뜻이면 건너뛴 것도 세야 맞다. 지금 코드는 "몇 번째로 제안을 보냈나" 에 가깝다.

둘 중 무엇이 맞는지 정하고 나서 고친다.
